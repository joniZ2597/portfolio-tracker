Notes
- **N1 "outcome identity":** where no production mutant exists for a family, the planted negative is the logic row's own exact-outcome check against the real recording: a changed decision changes the call sequence or the result, and the row fails (UNSCRIPTED_GIT or an outcome mismatch). No new mutant is added; if the Owner wants a new seeded variant for a family, it needs its own recording.
- **N2 `PL-17` rows run after PL-16's real push in the original suite**, so today they are refused at P5 ("nothing to push"), not at the record check. The scenarios reproduce exactly that sequence (land, push-request, push, then the bad record). This is existing behaviour, not changed here.
- **N3 oracle allowances (extensions to the brief's closed list; each is declared per scenario, never global; unlisted subcommands stay mutating):** `remote-read` (`git ls-remote`) is allowed in one moved scenario, the push-request of PL-53 (`pl53-push`); `object-only` is allowed in two (`pl53-protected`, `mut-oag4`, the protected-request tree build); `failed-mutating` (a mutating call that Git itself REFUSED, non-zero exit, so it changed nothing) is allowed in the three RS-2 overlap rows, whose decision IS Git's own `reset --keep` refusal. **Owner decision requested at G-MAP.**
- **N4 mutants and the oracle verdict:** a moved mutant is judged by its invariant (the unmutated control satisfies it, the mutant violates it), not by "nothing changed": a mutant may perform mutating calls with no net effect on the real repository (MUT-RS-5 replays a task onto an identical base), which the conservative oracle still reports as a change. Every non-mutant row requires oracle verdict = real verdict.
- **N5 file-system inputs:** the logic rows re-create the file-system inputs the verb read (approval records, audit log, lock, hook directories, manifest files, slot work files, untracked files of a slot, git worktree marker files) from the recorded scenario; times are normalised to `<ts>`.
